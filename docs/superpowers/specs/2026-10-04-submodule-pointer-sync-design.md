# 서브모듈 develop 포인터 자동 갱신 설계

## 목적과 합의

gods-eye, gods-mlops, gods-watching의 develop 변경을 gods-system/develop에 자동으로 채택한다. 검증을 통과한 포인터 변경은 봇이 직접 커밋한다. PR 생성, 예약 실행, workflow_dispatch 진입점, 제품 배포는 포함하지 않는다.

후보가 해당 저장소의 develop에 속하는지 확인하고 세 서브모듈을 정확한 SHA로 체크아웃할 수 있는지 검증한다. 소스 저장소의 테스트 성공을 기다리거나 전체 제품 통합 테스트를 실행하는 정책은 아니다.

## 흐름

1. 각 소스 저장소의 develop push 워크플로가 gods-system에 repository_dispatch를 보낸다. 브랜치 삭제는 제외한다. 저장소 이름, ref, 이벤트 SHA, 원본 실행 URL을 진단 정보로 보낸다.
2. 수신 워크플로는 고정된 이벤트 유형, 허용된 세 저장소, develop ref와 필드 형식을 검증한다. 전달받은 URL이나 경로를 체크아웃 대상으로 사용하지 않는다.
3. 하나의 전역 동시 실행 그룹으로 수신 작업을 직렬화한다. 진행 중인 작업은 취소하지 않는다.
4. 실행 시작 시 슈퍼 저장소 develop과 세 소스 저장소 develop을 읽어 후보 SHA를 고정한다. 이벤트 SHA는 진단 정보이며 채택 버전을 직접 지정하지 않는다.
5. 매 실행에서 세 포인터 모두를 최신 상태와 비교한다. 서로 다른 저장소의 이벤트가 겹쳐 대기 실행이 합쳐져도, 다음 실행이 모든 소스의 변경을 발견하도록 한다.
6. 후보 커밋의 존재와 develop 소속을 검증하고 세 서브모듈을 고정 SHA로 체크아웃한다. 중첩 서브모듈이 존재하면 해당 고정 버전의 체크아웃도 검증한다. 소스의 프로그램이나 설치 스크립트는 실행하지 않는다.
7. 검증이 모두 통과하면 변경된 gitlink만 한 커밋으로 반영한다. 변경이 없으면 커밋 없이 성공한다. 검증이 실패하면 어느 포인터도 갱신하지 않는다.
8. 최신 슈퍼 저장소 develop에 fast-forward push한다. 외부 쓰기로 충돌하면 최신 기반에서 포인터 변경만 다시 구성하고 검증하는 제한된 충돌 처리를 수행한다. force push는 하지 않는다. 충돌이 계속되면 실패한다.

이 과정에서 실패를 이유로 새 워크플로를 예약하지 않는다. 다음 소스 변경 이벤트가 오면 세 저장소의 당시 최신 상태로 다시 검증한다. 이벤트 송신 자체가 실패하거나 다음 이벤트가 없다면 자동 복구 시점을 보장하지 않는다.

## 동시 변경과 실패 사례

- gods-eye에 A, B가 연속 반영된 뒤 작업이 시작되면 B를 채택할 수 있다. A를 별도 커밋으로 남길 필요는 없다.
- gods-eye와 gods-mlops가 함께 바뀌면 한 실행이 둘을 함께 채택할 수 있다.
- 늦게 도착한 과거 이벤트도 현재 develop을 조회하므로 과거 이벤트 SHA로 포인터를 되돌리지 않는다.
- 작업 중 새 커밋이 생기면 현재 고정한 후보를 처리하고 후속 변경 이벤트가 최신 상태를 처리한다.
- 하나의 후보라도 검증이 실패하면 이번 갱신 전체를 반영하지 않는다. 세 포인터를 함께 검증한다는 정책의 결과다.
- develop 이력이 강제로 재작성되면 현재 develop을 기준으로 검증한다. 과거 포인터와의 조상 관계를 추가 승인 조건으로 두지 않는다.

## 인증과 신뢰 경계

GitHub App을 네 저장소에 설치하고 App ID와 비공개 키를 Actions 설정에 제공한다. App의 Contents 권한은 dispatch API가 요구하는 write를 포함해야 한다. 이 권한이 설치 대상 소스 저장소에도 적용될 수 있다는 점을 설치 안내에 명시한다.

실제 발급 토큰은 역할별로 좁힌다. 송신 토큰은 gods-system의 Contents write, 수신 시 소스 체크아웃 토큰은 세 소스의 Contents read, 포인터 push 토큰은 gods-system의 Contents write로 한정한다. App에 Workflows 수정 권한이나 관리자 권한은 부여하지 않는다. 워크플로 파일의 최초 도입은 개발자의 배포 절차로 수행한다.

개인 gh 로그인 토큰을 Actions 시크릿으로 복사하지 않는다. 비공개 키와 토큰을 로그에 출력하거나 저장소에 커밋하지 않는다. 외부 이벤트 필드는 명령 문자열에 직접 삽입하지 않고 데이터로 처리한다. 저장소와 경로의 대응은 수신 코드에 고정한다.

## 파일과 책임

- 세 소스 저장소: develop 변경을 알리는 작은 송신 워크플로.
- gods-system: 이벤트 수신 워크플로, 후보 조회·검증·gitlink 갱신 로직, 해당 로직의 회귀 테스트.
- gods-system 문서: 용어집, 결정 기록, 인증 설치 절차, 실패 확인 방법.

코드는 사용자 지시에 따라 GPT Luna max 작업자가 작성한다. 각 저장소에서 전용 브랜치를 사용하고 다른 작업의 변경은 보존한다.

## 검증 및 완료 기준

로컬 임시 Git 저장소를 사용해 실제 gitlink 변경, 무변경 처리, 연속 변경의 최신 SHA 채택, 여러 소스의 동시 변경, 잘못된 이벤트, 후보 체크아웃 실패 시 무반영, push 충돌 시 타인의 변경 보존을 검증한다. 워크플로 구문과 허용 이벤트·권한 설정을 검사한다.

실환경 완료는 네 저장소에 워크플로가 반영되고 App 설정이 완료된 뒤, 실제 소스 develop 변경에서 송신·수신·포인터 커밋까지 확인한 상태다. 기존 CI에 영향을 주는지 확인하고 채택 SHA와 변경 파일 목록을 대조한다. App 등록이나 키 제공이 완료되지 않았다면 구현 검증과 실환경 활성화 상태를 구분해 보고한다.
